# CLAUDE.md

floe はエージェントが書いた HTML ページをローカルサーバー（`http://127.0.0.1:7325`）で表示・管理する Go の単一バイナリです。dotfiles（[azarashi](https://github.com/sukekyo26/azarashi)）の `profiles/bedrock/.agents/skills/artifact` にある JS 実装を移植し、データ（YAML）とテンプレートから文書を組み立てる機能と、検査付きの inline SVG 図を足します。

- 検証は `just ci`（CI と同じ内容）。golangci-lint は `just setup` で入る。
- 対応 OS は linux と darwin（amd64・arm64）。Windows はリンクのパス検査などの信頼境界を検証できないので対応しない。

## 誤りは、どの層も `usererr` の基盤で作って出す

ユーザーに見せる誤りは、層（データファイル・テンプレート・部品・テーマ・図・CLI・API）によらず `internal/usererr` で作り、集め、出す。層ごとに別の誤りの型・一覧・出し方を作らない。新しい検査や層を足すときも同じ。

- **作る**：ユーザーが直せる誤りは `usererr.Error`（`New`・`NewAt`・`NewIn`）にする。`fmt.Errorf` は、ユーザーが直せない失敗（floe の不具合、ファイルやネットワークの読み書きの失敗）だけに使う。直せる誤りを `fmt.Errorf` で返すと、floe の失敗（API なら 500）として出てしまう
- **文**：i18n の目録（`messages_en.go`・`messages_ja.go`、CLI だけの文は `messages_cli.go`）の鍵で書き、何をどう直せばよいかを言う。外のライブラリの英語をそのまま引数に入れるなら、`LIMIT:` を付ける
- **場所**：ファイル・行・列・JSON ポインタは `File`・`Line`・`Column`・`At` に入れ、文に `file:line:` を書かない。文に残すのは、データの項目のパス、図の部品の名前、パスそのものが主語の誤り（無い・ディレクトリでない）、text/template が文の中にしか持たない行だけ
- **集める**：1 つの段の中では、どの検査も走らせて `usererr.List` に `Add` し、互いに関係の無い検査は `usererr.Collect` でまとめる。最初の誤りで返さない。前の検査の結果を使う検査だけを、その結果に誤りがあれば飛ばす。止まるのは段と段の間だけ
- **失敗**：`Add`・`Collect` が返す失敗（usererr でない error）は、そのまま返して止まる。例外は、自分の部品・テーマを読む失敗で、使えない理由として出す（それを使わないページまで止めない）
- **指す誤り**：使えない部品・テーマを指す誤りは、その理由を `Under` に持つ（`usererr.Over`）。同じ部品・テーマを別の所から指す写し（`Placed`）の 2 回目は、一覧が「上に出したとおり」とだけ言う
- **1 回だけ言う**：同じ誤り（1 回目として言葉にした形で、場所・頭の文・下の字下げの行が全部同じもの）は、`Tell` が 1 回だけ言う。どこで作ったか、同じ `*Error` かによらない
- **1 回だけ読む**：共有のもの（自分の部品・テーマ、テンプレートのファイル、アイコン集）は、1 回の出力（`Library.Run`）の中で 1 回だけ読む。そのために、読む関数の結果（値と誤りの組）を覚える。これは読み直しを減らすためで、1 回だけ言うためではない
- **並べる**：並べ替えは `Sorted`（`Collect` も並べる）だけ。警告も `usererr.List` にする
- **出す**：誤りを言葉にするのは `usererr.Tell`、並べる（場所・字下げ・頭の `floe: `）のは `Report.Render` だけ。CLI・API・誤りのページはこの 2 つを使い、自分で型を見分けない。サーバーが送った `Report` も、`Report()` を持つ error として `Tell` に渡す

## floe の不具合や困ったことは、ユーザーに伝える

floe はエージェントが使う道具なので、エージェントが使っていて困ったことがそのまま直すべき点になる。次のどちらの場面でも、次のようなことに気付いたら、ユーザーに伝える。

- **使っているとき**：データファイル・テンプレート・部品・テーマでページを作っているとき
- **直しているとき**：floe 本体を直していて、頼まれた作業とは別の不具合に気付いたとき（試した入力で検査が漏れた、など）

気付くこと:

- 誤りの文が、何をどう直せばよいかを言わない（推測で直した）。行と列が原因を指していない
- 検査を通ったのに、ページが崩れて描かれる、または後の段で失敗する（検査の漏れ）。逆に、正しいデータを断る
- 同じものを何度も書き写す、回り道をしないと書けないなど、書きづらい

伝え方:

- 気付いた時点で、作業の報告の中で伝える。作業の終わりまでためない。
- 回避して作業を続けたときも、回避したことと、その方法を伝える。黙って回避しない。
- データファイルの断片と floe の出力をそのまま添え、どこで困ったか、直し方の案があればそれも書く。
- floe 本体を直すかはユーザーが決める。頼まれた作業の中で、断りなく直さない。直している途中で見つけた別の不具合も、今の PR に混ぜない。

ページにも書く:

- 載せるかはユーザーに聞かない。使っているときに見つけたものも、直しているときに見つけたものも、気付いた時点で載せ、報告の中で載せたことを伝える。
- 伝えた問題は、floe のページ「floe の不具合と困ったこと」（slug は `floe-usage-issues`、データファイルは `~/.local/share/floe-plans/floe-usage-issues.yaml`）に追記し、`floe publish` で公開し直す。問題ごとにページを増やさない。
- 先頭のまとめの表（問題・困ること・急ぎ・直す大きさ）に 1 行足し、問題の節を 1 つ足して「何が起きるか」（データの断片と floe の出力）、「なぜ困るか」、「どう直すか」を書く。
- すでに載っている問題なら、その節に新しい例を足す。直ったら、まとめの表の急ぎを「直した」にし、直した PR を書く。
