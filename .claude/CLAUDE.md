# CLAUDE.md

floe はエージェントが書いたページをローカルサーバー（`http://127.0.0.1:7325`）で表示・管理する Go の単一バイナリです。データ（YAML）とテンプレートから文書を組み立て、検査付きの inline SVG 図を描きます。

- 検証は `just ci`（CI と同じ内容）。golangci-lint は `just setup` で入る。
- 対応 OS は linux と darwin（amd64・arm64）。Windows はリンクのパス検査などの信頼境界を検証できないので対応しない。

## 検査の方針

floe が入力を断る検査は、次の 4 つのどれかに当たるものだけにする。当たらない検査や特例は入れない。

- **ライブラリが返す誤り**：YAML・JSON Schema・html/template・expr などが返す誤りを、ライブラリの言葉のまま出す。言い直さない。場所は、ライブラリが返す分だけ付ける（JSON ポインタを YAML の行と列に写すのはよい）
- **信頼境界**：パス、CSP、サンドボックス、大きさなど、floe の外へ出る・外から入るものを守る。文脈によらない保守的な決まりで断る
- **floe 自身の仕組みの確かめ**：floe が置いた印や、floe がスタイルを入れる所など、floe の仕組みが前提にするものを確かめる
- **ライブラリの黙った読み違い**：ライブラリが誤りを出さずに、書いたのと違う値を読む所（YAML の 2 つ目の文書、`#` で値が切れる、`{a, b: 1}`、文字でない鍵、`.inf`・`.nan`）を断る

## 作りの決まり

- **使えない自分のものは止める**：描かずに分かる誤りで使えない自分の部品・テーマ・テンプレートが 1 つでもあれば、その出力を止めて理由を並べる。使った所だけで断る仕組みは作らない
- **集めるのは楽な所だけ**：1 つの段の中で、互いに関係の無い検査は集めて一度に出す。集めるために特例や推しを足さない。例外：解けない $ref のうち `$defs` の直下の 1 段と、断った URL・無い部品は、埋めてコンパイルし直して 100 まで言う（止める形が混ざると全部は言わない。上流が順を決めないため。S4）
- **外の振る舞いを真似ない**：HTML・CSS・URL・JSON Schema などは、本物のパーサやライブラリを使う。自分で読む作りにしない
- **受け入れた退行**：上に当たらない漏れは、`LIMIT:` のコメントと PR の本文に書く。検査は足さない

- **schema の形はコンパイルした木から**：floe が要る形（どの項目がどの部品・format か）は、コンパイルした `*jsonschema.Schema` から取る。schema の JSON を自前で辿らない（生の JSON を見るのは `$schema` の確かめだけで、schema の鍵の意味は読まない）。`$schema` は 2020-12・2019-09 だけを受ける。例外：S4 の埋める繰り返し（`holes.fill`）は、doc の根と `$defs` の直下だけを読み、書くのは写しだけ
- **木を歩くのは 2 つだけ**：schema の木を歩くのは、全部の欄を辿る `every` と、描く歩きの `followFrom`（`schema.Follow` の繰り返し）だけ。描く歩きも確かめる歩きも `schema.Follow` を使い、検査ごとに歩きを書き分けない。例外は 2 つだけ：`$schema` を見る生の JSON の歩き（schema の意味を読まない）と、根の値にいつも当たる schema の required を見る `sharedKeys`
- **YAML は yamlpos だけが読む**：YAML のバイト列を goccy に渡すのは `yamlpos` だけ。`yamlpos` の外（テストを除く）から import できる goccy のパッケージは `ast` だけ（depguard の規則 `goccy-in-yamlpos`）。値にするのも `yamlpos.Decode`
- **schema の JSON は schema だけが読む**：schema.json などの JSON のバイト列を読むのは `schema` の `read` だけ。`schema` の外からは、バイト列を `Compile`・`NewResource` に渡す。jsonschema を import できるのは `internal/schema` だけ（depguard の規則 `jsonschema-in-schema`）

決まりは、それを入れた PR がこのファイルに足す。

## 誤りの出し方

- **作る・包む**：ユーザーが直せる誤りは `usererr.Error` にする。ライブラリの誤りは `usererr.Library` で包み、文を言い直さない。`fmt.Errorf` は、ユーザーが直せない失敗（floe の不具合、読み書きの失敗）だけに使う
- **文を足さない**：usererr の誤りを `fmt.Errorf` で包んで文を足さない（`Tell` は包んだ側の文を言わない）。場所や名前は usererr の引数か場所に入れる
- **出す**：誤りを言葉にするのは `usererr.Tell`、並べるのは `Report.Render` だけ。目録の鍵は、それを使うコードと同じ PR で、英語と日本語の両方に入れる

## floe の不具合や困ったことは、ユーザーに伝える

floe はエージェントが使う道具なので、エージェントが使っていて困ったことがそのまま直すべき点になる。次のどちらの場面でも、次のようなことに気付いたら、ユーザーに伝える。

- **使っているとき**：データファイル・テンプレート・部品・テーマでページを作っているとき
- **直しているとき**：floe 本体を直していて、頼まれた作業とは別の不具合に気付いたとき（試した入力で検査が漏れた、など）

気付くこと:

- 誤りの文が、何をどう直せばよいかを言わない（推測で直した）。行と列が原因を指していない
- 検査を通ったのに、ページが崩れて描かれる、または後の段で失敗する（検査の漏れ）。逆に、正しいデータを断る
- 同じものを何度も書き写す、回り道をしないと書けないなど、書きづらい

伝え方:

- 気付いた時点で、作業の報告の中で伝える。作業の終わりまでためない。
- 回避して作業を続けたときも、回避したことと、その方法を伝える。黙って回避しない。
- データファイルの断片と floe の出力をそのまま添え、どこで困ったか、直し方の案があればそれも書く。
- floe 本体を直すかはユーザーが決める。頼まれた作業の中で、断りなく直さない。直している途中で見つけた別の不具合も、今の PR に混ぜない。

ページにも書く:

- 載せるかはユーザーに聞かない。使っているときに見つけたものも、直しているときに見つけたものも、気付いた時点で載せ、報告の中で載せたことを伝える。
- 伝えた問題は、floe のページ「simple-core の不具合と困ったこと」（slug は `floe-sc-usage-issues`、データファイルは `~/.local/share/floe-plans/floe-sc-usage-issues.yaml`）に追記し、`floe publish` で公開し直す。問題ごとにページを増やさない。番号は `S` を付けて見つけた順にする。
- develop にだけある問題は `floe-usage-issues` に置く。develop の問題で、このブランチが設計で避けるものも、そちらに置き、どう避けるかを書く。
- 先頭のまとめの表（項番・問題・種別・場所・困ること・急ぎ・直す大きさ・直す PR）に 1 行足し、項番は S を付けた番号を問題の文と分けて書く。直す PR には、直す予定の PR（B6 など）か「未定」を書く。問題の節を 1 つ足して「何が起きるか」（データの断片と floe の出力）、「なぜ困るか」、「どう直すか」を書く。
- 種別は 1 つの pill で、表の下の注「種別と場所の見方」の言葉と色（バグ・改善・リファクタリング・ドキュメント・案）から選ぶ。場所は直す所を書く。
- すでに載っている問題なら、その節に新しい例を足す。直ったら、「残っている問題」の表の行と問題の節を消し、「直した問題」の表に、項番・問題・直した PR（何をしたかを一言）・マージした日の 1 行を足す。
